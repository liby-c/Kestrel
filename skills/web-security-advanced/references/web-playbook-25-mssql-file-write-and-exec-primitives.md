# MSSQL受限账户下的文件写入与命令执行原语
English: MSSQL File Write and Command Execution Primitives under a Low-Privilege Service Account
- Entry Count: 7
- Use this file to shortlist relevant primitives, then open the linked source markdown for the full workflow and commands.
- Note: 本条为**实战提炼**（非上游提取），内容自包含，无需外部源文档。
- Note: 本文件**只收录方法论与能力原语**（调用结构 + 判据 + 陷阱），**不收录成品 payload / 可直接复制的完整命令**。

适用范围：已取得 SQL Server 高权限（`sa` / sysadmin）的任意 T-SQL 执行能力，但目标服务账户是**最小权限虚拟账户**（如 `NT Service\MSSQLSERVER`），导致常见命令执行路径逐一受阻。

本文回答两个问题：
1. **该用哪条执行原语**——以及每条失败时释放出什么信号、该切到哪里；
2. **文件该往哪写**——在不知道 Web 物理路径时如何定位落点并验证可写。

## 执行原语优先级与失败模式
- ID: mssql-exec-primitives
- Difficulty: intermediate
- Subcategory: 命令执行
- Tags: mssql, rce, xp_cmdshell, ole-automation, clr, sql-agent, execution-primitive
- Source: 实战提炼（Windows Server 2012 R2 + IIS 8.5 + SQL Server 2014）
Description:
在受限服务账户下按优先级尝试四条命令执行原语，依据**失败模式**判断该切到哪条，而不是在单一方向上反复变形硬撞。
Prerequisites:
- 已具备任意 T-SQL 执行能力，且语句回显可稳定取回
- 已确认当前数据库身份具备 sysadmin
Execution Outline:
1. 1. 按优先级依次尝试四条原语
2. 2. 逐条记录失败模式与错误码
3. 3. 命中特定失败模式立即切换，不重复硬撞

**优先级与判据**：

| 顺序 | 原语 | 由谁执行 | 生效条件 | 典型失败模式 |
|---|---|---|---|---|
| 1 | `xp_cmdshell` | sqlservr 服务账户 | 该账户具备进程创建所需登录权限 | `CreateProcess` 错误码 5（缺「以批处理方式登录」） |
| 2 | OLE Automation | sqlservr 进程内 COM | OLE 已启用 + 目标目录可写 | 对象**可创建**但方法调用**无副作用** |
| 3 | CLR 程序集 | sqlservr 进程内 CLR | `clr enabled` 能开启 | 配置无法开启 / 程序集创建被拒 |
| 4 | **SQL Server Agent 作业** | **Agent 服务自身账户** | Agent 服务在运行 | 脚本宿主被执行策略拒绝 |

**CLR 原语的两个判据**（避免在「能不能开 CLR」上误判）：

- **版本判据**：「强制 CLR 安全」这类配置项**仅存在于较新版本**；在旧版本上查询会报
  「配置选项不存在，也可能是高级选项」——可据此反推目标版本区间，不要误判为权限不足。
- **生效值判据**：配置项有「当前值」与「生效值」两个字段；**改动后生效值可能仍是旧值**
  （需重新配置 / 重启才刷新）——只看「当前值已启用」会误判为已生效。
- 启用 CLR 后仍需**先创建自定义程序集**才能执行托管代码；库内预置的程序集（如地理 / 类型类）不可用于执行。

**为什么 Agent 原语往往一次成功（尽管排在最后尝试）**：
Agent 是**独立服务、拥有独立服务账户**。命令由 **Agent 进程**而非 sqlservr 创建，
因此**不受 sqlservr 账户进程创建策略的约束**；实测其执行身份可显著高于 sqlservr 账户。

**Agent 原语的调用结构（三步）**：

1. 创建作业 → 添加步骤（子系统选「操作系统命令」）→ 启动作业
2. 输出经**作业历史**回读（无需文件落盘，也不依赖 HTTP 可达）
3. 作业历史中记录每步的**执行身份 / 返回码 / 输出**

**要点与陷阱**：

- **输出走作业历史**，不落盘、不依赖 Web 可访问，是最干净的取回方式
- **阶梯法**：把多条待验证假设各建成一步，并设置「无论成败都继续执行」，
  一次查询即可看到全部步骤结果 —— 大幅节省往返轮次
- **脚本宿主（图形宿主与命令行宿主）在该作业中可能被「拒绝访问」**：
  此时改用命令解释器内置能力，或经系统自带下载能力引入独立工具
- **「拒绝访问 + 退出码 1」是程序级拦截，不是长度限制（★易误判）**：
  用一个**远小于实测上限**的极短同程序调用做对照——若同样被拒，即确认是**对该可执行程序本身的拦截**，
  继续缩短命令不会有任何收益。反面教训：曾据一次长命令失败推断为「命令长度限制」，
  而后用不足百字节的同类命令复现同一拒绝，才确认为程序级拦截。
- 命令长度上限宽松（实测千字节级无问题）
- **输出回读有长度上限**：作业历史的输出字段是**定长上限字符串**（实测约 4000 字符），
  超长输出会被**静默截断**。取长文本时应**按步骤分段读取**，并对单个字段做长度裁剪，
  不要把全部输出压进一个查询。
- **stdout 自动入历史，重定向不一定落盘**：命令解释器的输出通常会被作业框架**自动捕获写入历史**；
  而「输出重定向到文件」在该上下文中**可能不生效**（跨账户 / ACL 因素）。
  因此回显**优先走作业历史**，不要依赖文件落盘。
- 排查失败时**必须读「步骤历史」**，只看作业整体状态拿不到原因与退出码；
  应读取「步骤序号 / 执行状态 / 消息正文」三列。
- **目标间歇不可用时用「轮询 + 重试」，而非线性等待**：Web 应用池会周期性挂起（表现为固定超时），
  单次超时 **≠** 操作失败；应隔数十秒重试，并把长任务改为**轮询作业历史**直到目标步骤出现。

**决策原则**：
**出现「错误码 5」类拒绝即应切换原语**，不要在同一原语上反复变形。
实战中，在 `xp_cmdshell` 与 OLE 上多轮变形的收益为零，而**从未被尝试的 Agent 原语一次成功**。

## 阻断诊断：「错误码 5」是一个家族
- ID: mssql-access-denied-family
- Difficulty: basic
- Subcategory: 阻断诊断
- Tags: mssql, access-denied, sebatchlogonright, troubleshooting, low-privilege
- Source: 实战提炼
Description:
识别「动作已触达操作系统但被 AC L拒绝」这一状态，并认识到它会在多个不同动作上同时出现——根因是同一个账户权限上限，而非各自的配置问题。
Prerequisites:
- 已能取回 T-SQL 语句的原始错误信息
Execution Outline:
1. 1. 收集各处出现的「错误码 5」
2. 2. 归纳是否同源
3. 3. 按决策树选择：改权限 或 换原语

**同一账户权限上限在四个不同动作上同时表现为「拒绝访问」**：

| 动作 | 表现 | 被拒的层面 |
|---|---|---|
| 调用 `xp_cmdshell` 创建进程 | `CreateProcess` 失败，错误代码 5 | 进程创建 / 登录权限 |
| 写注册表 HKLM | 注册表 API 返回错误 5 | 注册表 ACL |
| 批量读取系统配置文件 | OS 错误代码 5（拒绝访问） | 文件 ACL |
| Agent 作业执行脚本宿主 | 进程退出码 1 + 拒绝访问 | 进程创建 / 执行策略 |

**统一根因**：SQL Server 服务账户（如 `NT Service\MSSQLSERVER`）是**最小权限虚拟账户**，
这是现代 SQL Server 的**安全默认值**，不是配置错误。

**佐证方法（区分「被策略拒」与「被模板 / WAF 拦」）**：

- **首次调用耗时异常长**（实测约 35 秒，等于等待进程创建超时），后续调用立即失败
- 错误内容**与命令本身无关**（不存在的命令同样报错误码 5）
- 多次重复**稳定复现**同一错误码

**决策树**：

```
出现「错误码 5」
  ├─ 需要在该账户下执行命令 → 提升该账户的本地安全策略（需主机侧操作，属系统配置变更）
  └─ 需要执行命令但可换身份 → 改走 Agent 原语（独立服务账户）★
  └─ 仅需写文件           → 改走 OLE 写文件原语（进程内 COM，不创建进程）
```

**关键判断**：
1. **「进程创建被拒」不等于「文件写入被拒」**，二者受不同策略约束；
2. **同一「错误码 5」在多处出现 = 账户权限上限**，继续变形 payload 不会改变结果。

## 反向连接的前置条件
- ID: mssql-reverse-connect-prereq
- Difficulty: intermediate
- Subcategory: 反向连接
- Tags: mssql, reverse-shell, egress, listener, prerequisites
- Source: 实战提炼
Description:
取得命令执行能力 **≠** 能建立反向连接。反向连接额外需要「TCP 客户端能力」，而命令解释器本身不具备该能力。本条目只描述**前置条件与验证判据**，不含任何 payload。
Prerequisites:
- 已取得任意命令执行原语（见「执行原语优先级」）
- 已有一个**目标可主动连入**的监听端
Execution Outline:
1. 1. 确认监听端的可达性
2. 2. 选定 TCP 客户端载体
3. 3. 经命令执行原语投放并触发
4. 4. 在监听端核对来源 IP 验证

**三个必要环节**：

| 环节 | 要求 | 常见障碍 |
|---|---|---|
| **监听端** | 目标能主动连入 | 监听端位于 NAT 后需端口映射；云主机需**安全组放行**该端口 |
| **载荷** | 内置回连地址与端口，且架构/位数匹配 | 生成后需**先验证自身可从该地址下载** |
| **投放** | 经命令执行原语落到目标并触发执行 | 目标可能限制脚本宿主执行（见上文陷阱） |

**TCP 客户端载体的可选路径**（按省事程度排序）：

1. **系统自带脚本宿主** —— 最省事，无需下载；但可能被执行策略 / ACL 拒绝
2. **独立 TCP 工具** —— 需先经系统自带下载能力引入（依赖目标出网能力）
3. **命令解释器本身** —— **不具备 TCP 能力**，无法直接建立连接

**验证判据**：

- 监听端出现**来自目标 IP** 的连接，且收到目标回传的标识信息（如主机名 / 当前用户）
- **必须核对来源 IP**：暴露在公网的监听端口会持续被随机扫描器连接，
  这些连接的来源与目标无关，**不可当作成功证据**

## 文件写入前的路径发现（哨兵遍历法）
- ID: mssql-path-discovery
- Difficulty: intermediate
- Subcategory: 路径发现
- Tags: mssql, file-write, path-discovery, web-root, marker-file
- Source: 实战提炼（Windows Server 2012 R2 + IIS 8.5 + SQL Server 2014）
Description:
不猜路径。用「已知必定存在的文件」当**哨兵**遍历磁盘，命中后在该目录**写一个标记文件**，再经 **HTTP 读回**——一步同时确认三件事。
Prerequisites:
- 已具备任意 T-SQL 执行能力，且**执行通道允许调用系统扩展过程**（见「目录枚举与上下文约束」）
- 目标磁盘上确实存在待定位的站点目录
Execution Outline:
1. 1. 选定哨兵文件
2. 2. 遍历磁盘找命中目录
3. 3. 命中目录写标记文件（内容 = 该目录绝对路径）
4. 4. HTTP GET 读回标记文件
5. 5. 处理鉴权陷阱（改到匿名站点目录重做）

**一步三确认**：

| 确认项 | 依据 |
|---|---|
| 该目录是 Web 站点根 | 目录内存在 Web 入口文件（登录页 / 站点配置文件 / 首页等） |
| 该目录**可写** | 标记文件写入成功 |
| 该目录**可经 HTTP 访问** | 能 GET 到标记文件内容 |

**步骤 1 · 选哨兵**（必定存在、且文件名有辨识度）：

- 应用入口类：登录页、首页、全局应用类文件
- 配置与静态类：站点配置文件、首页静态文件、站点图标
- 建议用**多个哨兵**交叉验证，避免单点误判

**步骤 2 · 遍历磁盘**：见「目录枚举与上下文约束」。

**步骤 3 · 写标记文件**：

- 文件名随机、不显眼
- **内容 = 该目录的绝对路径字符串**
- 写入成功即证明该目录可写

**步骤 4 · HTTP 读回**：请求该标记文件，期望返回其中的绝对路径。

**步骤 5 · 关键陷阱——站点鉴权会拦标记文件的读取**

命中目录若属于**有页面级鉴权**的站点，标记文件虽写入成功，但 HTTP 读取会被重定向拦截。
此时**不要放弃**，而是改在**同主机匿名可达的站点目录**做同样动作——同主机多站点场景下，
通常至少存在一个未授权可访问的站点。

**变体（同主机多站点）**：在多个站点目录各写一份标记，逐一 HTTP 试探，
可一次性建立「目录 ↔ 端口」的完整映射。

## 目录枚举与上下文约束
- ID: mssql-xp-dirtree
- Difficulty: basic
- Subcategory: 文件系统枚举
- Tags: mssql, xp_dirtree, directory-enumeration, execution-context
- Source: 实战提炼
Description:
用目录树扩展过程一次性递归列出目录，快速定位含哨兵文件的目录；同时必须弄清**执行通道的上下文**，否则该原语会整体失效。
Prerequisites:
- 当前登录具备执行该扩展过程的权限（sysadmin 具备）
- **执行通道位于「顶层语句」而非「远程查询上下文」**
Execution Outline:
1. 1. 确认执行通道的上下文
2. 2. 指定起始路径与递归深度执行
3. 3. 解析「相对路径 + 深度 + 是否文件」输出
4. 4. 命中哨兵即拼接出绝对路径

**★ 上下文约束（本条目最关键的一点）**：

| 执行通道 | 能否调用系统扩展过程 |
|---|---|
| **注入的顶层语句**（堆叠查询） | ✅ 可以 |
| **远程查询上下文**（如 `openrowset` / 链接查询内部） | ❌ **禁止** —— 编译期即报「无法确定元数据…调用扩展存储过程」 |

**因此**：若执行的 T-SQL 被包在远程查询上下文中，本原语与 `sp_OACreate` 等**全部失效**，
必须先把执行通道改为**顶层语句**（堆叠查询构造）。

**参数与输出**：依次为「起始路径 / 递归深度（0 表示无限）/ 是否包含文件项」。
输出为三列：相对路径 / 深度 / 是否文件。**命中哨兵文件名即可推出该目录的绝对路径**。

**优点**：单次调用返回整棵子树，无需循环，远快于逐目录判断存在性。

**注意**：

- 返回的是**相对路径**，需与起始路径拼接
- **深度 0 全递归在大磁盘上会超时**，建议先限深度、再逐层下钻
- 无该过程权限时，备选「文件系统类 COM 对象」逐目录判断（慢）
- **扫描顺序**：先已知线索路径（如报错泄露的源码路径所在盘）→ IIS 默认站点目录 → 其他数据盘

## 写文件（OLE Automation）
- ID: mssql-ole-file-write
- Difficulty: intermediate
- Subcategory: 文件写入
- Tags: mssql, ole-automation, sp_oacreate, file-write, filesystemobject
- Source: 实战提炼
Description:
当命令执行被拒时，用 OLE Automation 完成文件写入——它是**进程内 COM，不创建新进程**，
因此不受进程创建相关本地安全策略约束。本条目强调**调用结构与诊断陷阱**，不提供可直接复制的语句。
Prerequisites:
- sysadmin 权限（启用 OLE 配置项需要）
- 目标目录对 **SQL Server 服务账户**可写
- 执行通道为顶层语句（见「目录枚举与上下文约束」）
Execution Outline:
1. 1. 确认 OLE 配置项已启用
2. 2. 按四步结构调用
3. 3. 每次调用后取真实错误
4. 4. 按陷阱清单排查「无副作用」现象

**步骤 1 · 确认配置项已启用**

需确认 OLE Automation 相关配置项的**生效值**为启用状态（启用前需先放开高级选项）。
仅凭"对象能创建"不足以判断——但若对象创建成功且无错误，通常说明已启用。

**步骤 2 · 四步调用结构**：

| 步骤 | 动作 | 必须做的事 |
|---|---|---|
| ① 创建对象 | 以「文件系统类」COM 对象为目标创建 | **确认返回句柄非 0** |
| ② 调用方法 | 依次调用「创建文本文件 / 写入 / 关闭」 | **必须接收 OUTPUT 返回值** |
| ③ 取真实错误 | 取错误来源与描述 | **每次调用后必做** |
| ④ 释放对象 | 销毁对象句柄 | —— |

**步骤 3 · 陷阱清单（本条目核心价值）**：

1. **「调用返回成功」≠「动作生效」**
   COM 方法内部失败时**不一定会抛异常**，外部看起来是"执行成功但零副作用"。
   → 必须**接收方法返回值**，并用"等待完成"模式读取真实返回码。
2. **只有错误信息过程能给出真实原因**
   不要依赖 SQL 层的成功标志，也不要只看返回值。
3. **不要归因于不存在的辅助过程名**
   OLE 相关存储过程是一个**固定的七个成员的集合**：
   `sp_OACreate` / `sp_OADestroy` / `sp_OAGetErrorInfo` / `sp_OAGetProperty` /
   `sp_OAMethod` / `sp_OASetProperty` / `sp_OAStop`。
   其中**没有**任何"字符串包装"或"释放"之类的额外过程（释放用 `sp_OADestroy`，取错误用 `sp_OAGetErrorInfo`）。
   实战中曾因假设存在此类过程而**连续两轮误判方向**——这是本原语最典型的分析陷阱，务必规避。
4. **目录可写性独立于原语可用性**
   即使 OLE 完全正常，若目标目录 ACL 未授予服务账户写权限，仍会失败。
   先用"写标记文件"验证可写性，再谈落点。
5. **★ 输出参数的【位置】是硬契约（本原语最反直觉的一点）**
   方法签名中，输出参数位于**方法名之后、输入参数之前**；把它放到参数列表**末尾**
   会直接报「sp_OAMethod 用法: ObjPointer int IN, MethodName varchar IN [, @returnval &lt;any&gt; OUT [, ...]]」。
   - 收到该「用法」报错 = **参数形状错，不是权限错、更不是对象不可用**——不要据此切换原语；
   - 把返回值参数**前置**后，同一调用立即生效（实测：前置后句柄非 0 且文件真实落地）。
   - **有返回值的方法**：必须接收该输出参数，否则只是"执行成功但零副作用"。
   - **无返回值（void）的方法**：**不得**接收输出参数，否则报
     「参数中存在错误，或者尝试从不提供返回值的方法中检索返回值」。
   → 先判断方法**有没有返回值**，再决定调用形态，是使用本原语的前提。
6. **对象创建成功 ≠ 对象可用，用两个探针分辨**
   - **创建返回句柄**：非 0 = 类可实例化；`0` / `-1` = 类未注册 / 未启用 / 线程公寓不匹配
     （HRESULT 会给出具体原因，应读取）。
   - **读属性探针**：对同一对象读一个已知属性，能取回值即证对象真实可用，与方法调用互相印证。
   - 具备以上探针后，才能把"方法无副作用"精确定位到**调用形态**（陷阱 5），而非对象本身。

**写入途径的优先级**（命中即用，不必穷举）：

| 顺序 | 途径 | 依赖 |
|---|---|---|
| 1 | **OLE Automation（文件系统类对象）** | OLE 已启用 + 目标目录可写 **← 优先** |
| 2 | 命令执行原语 + 输出重定向 | 进程创建权限（常被拒，见「错误码 5 家族」） |
| 3 | 老旧的文件写出过程 | 仅存在于老版本或额外组件 |
| 4 | 数据库备份到文件 | 只产出备份格式，**不可作脚本载荷**，仅可用于路径探测 |

## 堆叠执行通道的语句级约束
- ID: mssql-stacked-batch-constraints
- Difficulty: intermediate
- Subcategory: 注入工程
- Tags: mssql, stacked-query, batch, injection-engineering, execution-context
- Source: 实战提炼
Description:
「注入点支持堆叠」只是入场券。堆叠把多条语句拼进**同一编译批次**，该批次随后受 SQL Server 的语句级规则约束——不满足时表现为**与 payload 内容无关的固定报错**，极易被误读为"权限不足"或"注入不成立"。
Prerequisites:
- 已确认某参数位于可闭合的字符串上下文，且目标支持多语句
- 已能稳定观察到服务端回显的**原始错误文本**
Execution Outline:
1. 判定模板残片是否单行（决定行注释可用性）
2. 处理批次级变量作用域
3. 处理"必须是批次首语句"的 DDL
4. 处理不能在远程查询上下文的配置语句

**判据一 · 模板残片必须单行（决定行注释是否可用）★最高优先**

注入值落在应用模板的字符串常量内；闭合引号后**残留的模板片段**决定后续语句能否成型：

| 残片形态 | 单行注释（`--`）效果 | 结果 |
|---|---|---|
| 残片**全部在同一行** | 一次注释掉整段残片 | ✅ 可用 |
| 残片**跨多行** | 只能注释首行，后续行仍在语句内 | ❌ 语法错（与 payload 无关，稳定复现） |

→ **选注入点时优先选「残片单行」的端点。** 同一应用内不同端点的模板可能不同——
同一业务字段在不同接口下的残片形态不一致，因此应**横向扫描「端点 × 字段」矩阵**，
而不是在单一端点上反复变形。（实战：一个端点残片跨 3 行全败；另一端点残片单行，一次成功。）

**判据二 · 批次内变量名必须唯一**

多条语句拼进同一批次时，`DECLARE` 的变量名**在该批次内不可重复**：

- 报错形态：`变量名 '@x' 已声明。变量名在查询批次或存储过程内部必须唯一。`
- 含义：**不是权限问题，是批次内重复声明**。
- 处置：每次调用改用不同变量名，避免同批次内多次 `DECLARE` 同名变量。

**判据三 · 部分 DDL 必须是批次首语句**

`CREATE PROCEDURE` / `CREATE FUNCTION` / `CREATE TRIGGER` 等要求**位于批次第一条语句**：

- 报错形态：`'CREATE/ALTER PROCEDURE' 必须是查询批次中的第一个语句。`
- 含义：**堆叠构造中无法直接创建过程**（注入残片已占用批次首部）。
- 处置：放弃"堆叠内建过程 / 触发器"的思路，改用其他原语；或另寻允许独立批次的执行通道。

**判据四 · 配置类语句不能在远程查询上下文**

`sp_configure` 一类语句若被包在 `openrowset` / 链接查询内部，报：

- `不支持对系统目录进行即席更新。`

与扩展过程同源——**远程查询上下文有独立的编译限制**（详见「目录枚举与上下文约束」）。

**通用方法论**：

> 拿到「语法错 / 用法错 / 已声明 / 必须首语句」这类**形状类报错**时，
> 首先判定这是**语句结构与批次约束**问题，而非权限问题；
> 不要据此切换执行原语，也不要判定注入不成立。
